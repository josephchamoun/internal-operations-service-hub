# ADR-001: Relational Database over a Document Store

## Context

The hub needs one system of record for requests and everything attached to them, teams, categories, priorities, users, messages, attachments, and a full event timeline per request. A choice has to be made about what kind of database holds that data, since it shapes almost everything downstream: how relationships are modeled, how invariants get enforced, and how the real queries the product needs actually get answered.

A few things about this data are already known and matter to the choice. Nearly every meaningful query joins a request against another entity, its team, its category, its messages, or its timeline, rather than reading a request in isolation. Several rules must never be violated, most importantly that a request can have at most one claimant at a time; two team members trying to claim the same request at nearly the same instant have to result in exactly one of them succeeding, never both, and never an unclear in-between state. The shape of the data is also fixed and well understood, teams, categories, and priorities are small, Admin-defined lists, not free-form or evolving structures. Volume is assumed to be low to moderate, not high-throughput or public-facing.

## Options considered

**Document store.** Each request could be stored as a single, self-contained document, with messages, attachments, and timeline events nested inside it. This fits data that's naturally hierarchical and read as a whole, and scales well for very high write volumes and flexible, evolving schemas.

**Relational database.** Requests, teams, categories, priorities, users, messages, attachments, and events are modeled as separate, related tables, connected through foreign keys, with queries expressed as joins across them.

**Hybrid, a relational core with a document store for messages or timeline events.** Keep the core entities relational, but move the append-only, high-volume pieces like messages or events into a document store.

## Decision

Use a relational database for the entire system, with no document store involved.

The main reason is that this data is a tightly connected network, not a set of independent documents, and a document store models exactly the wrong shape for it. Nearly every real query already identified in this design, a team loading its queue, a request's timeline, a message thread, requires joining across entities, which a relational database does natively and a document store either can't do at all or has to fake by duplicating data across documents and keeping the copies in sync by hand.

The claim invariant is the clearest, most concrete reason to reject a document store specifically. When two team members try to claim the same request at nearly the same moment, the write has to be atomic, the database itself has to guarantee only one of those writes succeeds, using the same transactional mechanism it already uses to enforce every foreign key in the schema. A relational database provides this guarantee directly. A document store offers no equivalent out of the box; that safety would have to be built and maintained by hand in application code instead, which is exactly the kind of race condition that's easy to get wrong.

The hybrid option was considered and rejected too. Splitting messages or events into a separate document store would mean running two different storage systems for data that's constantly read together, a request and its timeline are looked at side by side on nearly every open, so keeping them in the same relational database, joinable in a single query, is simpler and avoids a second system to keep consistent with the first.

Finally, none of the usual reasons to reach for a document store apply here. The schema is small and fixed, not evolving or deeply nested. Volume is modest, not the kind of write throughput that would strain a relational database. A relational database's referential integrity and transactional guarantees directly match the correctness rules this system actually needs, at no real cost given the scale involved.

## Consequences

Every entity, including attachments, lives in the same relational database, with foreign keys enforcing that a request always points to a real team, a real category, and a real priority, and that a message or an event always belongs to a real request. This is what lets a rule like "at most one claimant" be guaranteed by the database itself, not just hoped for in application code.

The tradeoff is that this design doesn't scale the way a document store would under very high write volume or a rapidly changing schema, but neither of those is expected here, so that tradeoff costs nothing today. If attachment volume or overall request volume ever grew far beyond what's assumed now, moving attachments into a separate object store would be the natural next step, not a change to this decision itself.
